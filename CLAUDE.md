# CLAUDE.md

Guidance for AI assistants working in this repository. Read this before making changes.

## Project

Authentication REST API: Express 5 + TypeScript (ESM, `nodenext`), PostgreSQL 17 via Drizzle ORM, Zod validation, JWT in `httpOnly` cookies, Resend for email, Multer + ImageKit for avatars. Package manager: **pnpm**.

The product is **CKAuth**, at `https://ckauth.chiragdev.com`. `frontend/` holds its React + Vite + Tailwind app, a separate pnpm package with its own lockfile. Production runs on a Hostinger KVM 2 VPS that also hosts other sites:
- A shared **edge Caddy** (`/opt/edge`, from `deploy/edge/`) owns ports 80/443 for every site and imports one `sites/<project>.caddy` per project.
- CKAuth's site file (`deploy/ckauth.caddy`) proxies `/api/*` (with `/api` stripped) to `ckauth-api` and everything else to `ckauth-web`. That makes it one origin, so no CORS.
- `api` and `web` deploy **independently**: separate images, the `API_TAG`/`WEB_TAG` tags, and the `api.yml`/`web.yml` workflows chosen by path filters, which share `deploy.yml` → `deploy/deploy.sh`.

- Human docs: `README.md` (setup), `docs/API.md` (endpoint contract), `docs/DEPLOYMENT.md` (production), `docs/SEO-AUDIT.md` (strict SEO/traffic tests, scores and the traffic plan), `docs/GLOSSARY.md` (every term the docs use). Docs are written for beginners but stay professional: keep the technical term and explain it on first use, and add new terms to the glossary
- Project history: `DEVLOG.md` (timeline), `LEARNINGS.md` (mistakes → rules)

## Commands

```bash
pnpm build          # type check + compile; run before every commit
pnpm dev            # watch mode on PORT (default 8080)
pnpm db:up          # start Postgres and Redis in Docker
pnpm db:generate    # create a migration after editing src/db/schema.ts
pnpm db:migrate     # apply migrations
cd frontend && pnpm build   # frontend type check + build (also run before every commit if frontend/ changed)
pnpm docs:artifact  # bundle the Markdown docs into .docs-artifact/ckauth-docs.html and warn about broken doc links
pnpm test           # the test suite (needs Postgres; uses its own ckauth_test database)
pnpm e2e            # browser end-to-end tests (Playwright; needs Postgres; builds both apps first)
pnpm perf           # measure the live site (read-only); pnpm perf:report prints the report. Run weekly by perf.yml
pnpm check:pr       # every pre-PR check: builds, knip, audits, tests, built-site and repo rules, docs links, leftover TODO(human)s
pnpm seed:activity  # dev only, after pnpm build: six fake users and a month of activity-log events; --clear removes them
```

`src/utils/mail.ts` creates the Resend client at import, so the server won't start without `RESEND_API_KEY` or `EMAIL_FROM`. No mail domain is hard-coded anywhere; it's always `EMAIL_FROM`. `imagekit.ts` creates its client on first use, so a missing ImageKit key only breaks avatar uploads.

**Tests** (`test/`, Node's built-in `node:test` run through `tsx`, no test framework): one file per area (`sign-up`, `verify-email`, `sign-in`, `session` (incl. the device list), `account` (profile, avatar removal, self-delete, resend, change email), `mail-failure` (every mail-sending endpoint still answers when its mail fails: any address at `@mail-fails.test` fails in memory mode), `password`, `upload-avatar`, `rate-limits`, `admin`, `activity` (every audit event, the rollback guarantee, `/admin/activity`, pruning), `metrics` (referral tags, the visit counter, sign-up sources, the stats' `referrals`), `redis-down`), plus unit tests for the Zod models, JWT helpers, error handler and `request-logger` (route templates, the allow-list, log levels), and `known-gaps.test.ts` (`test.todo` for each known gap below). `pnpm test:coverage` fails below 95% lines / 83% branches / 85% functions; CI runs it (`api.yml`, with a Postgres service) before building an image. Frontend unit tests (`frontend/test/`, run by Node directly) cover `validation.ts`, `device.ts`, `time.ts` and `api.ts`'s single-flight refresh and session-ended signal. **Browser tests** (`e2e/`, Playwright, `pnpm e2e`; sign-up and sign-in so far, not in CI yet): `playwright.config.ts` starts the API on 8090 through `e2e/start-api.ts` (its own `ckauth_e2e` database made by `prepareDatabase` from `test/global-setup.ts`, `MAIL_TRANSPORT=memory`, no Redis) and `vite preview` on 4180, and runs chromium, firefox, webkit and a Pixel 7 project. `e2e/fixtures.ts` gives each test a fake `X-Forwarded-For` (so per-IP limits don't trip), a fresh `email`, a `verifiedUser` and an `inbox` that reads the dev-only `GET /dev/outbox?to=` (404 unless `MAIL_TRANSPORT=memory`). Every integration test drives the real Express app over HTTP against a separate `ckauth_test` database, which `test/global-setup.ts` creates and migrates; `TEST_DATABASE_URL` overrides it. `test/env.ts` fixes the environment first: `MAIL_TRANSPORT=memory` keeps mails in `outbox` (`src/utils/mail.ts`) so a test reads the link a user would click, no Redis (fresh in-memory rate limits per file), no ImageKit, fixed secrets, `LOG_LEVEL=silent`. Helpers in `test/helpers.ts`: `Client` (cookies, plus its own IP per client so per-IP limits behave), `createUser`, `signIn`, `signUp`, `lastMailTo`, `tokenFrom`, `findUser`, `sessionsOf`. Call `startApp()` at a test file's top level, never inside a hook. A new endpoint or rule gets tests in the same change, and a check that can't fail proves nothing: break the code once and watch the test fail.

For anything the suite can't cover (real emails, ImageKit, the browser), also run the real flow against a local server on a spare port (`PORT=8081 node dist/index.js`) so the user's dev server on 8080 is left alone, and clean up test users and uploaded files afterwards.

## Layout

- `src/app/auth/routes.ts`: route → middleware → `authController.handleX.bind(authController)`
- `src/app/auth/controller.ts`: `AuthController` class, one `handleX` method per endpoint
- `src/app/auth/models.ts`: Zod schemas named `<thing>PayloadModel`
- `src/app/auth/middleware.ts`: `authenticateToken` (sets `req.user`, including `role`, and `req.sessionId`, read from the database on every request; 401 once the token's session row is gone; rejects unverified users) and `authorizeRoles(...roles)` (403 unless `req.user.role` is listed; always after `authenticateToken`)
- `src/app/auth/utils/sessions.ts`: `startSession(executor, userId, req)` is the only way to start a session (one `sessions` row per device, max 10 per user, the access token carries its `sid`); `setSessionCookies`/`clearSessionCookies`. Ending a session = deleting its row. `user-columns.ts`'s `safeUserColumns` is the one list of user fields a client may see (`req.user`, profile edits, the admin list); select through it, never by hand. `users.refresh_token`/`reauthenticated_at` are unused leftovers kept for rollbacks; sudo mode lives on `sessions.reauthenticated_at`
- `src/app/auth/utils/constants.ts`: `userRolesEnum` (`user`, `admin`) is the single source of the role values; `schema.ts`'s `user_role` Postgres enum and the Zod models are built from it. `PASSWORD_HASH_ROUNDS` lives here too
- `src/app/admin/`: same layout as `auth/` (routes, controller, models, `middleware.ts` with `requireRecentReauth`), mounted at `/admin`; `router.use(authenticateToken, authorizeRoles('admin'))` guards every route. Endpoints: stats, users (paged, `?search=`), `reauth` (sudo mode), invite (`POST /users`, a 72-hour set-password link through the reset flow) and delete (emails a verified user). Admins can't delete themselves or other admins through the API. `GET /activity` reads the audit log (filters `?action=`, `?userId=`; never returns IPs)
- `src/app/metrics/`: `POST /metrics/visit` (no auth) counts visits from our own tagged links (`?ref=x`) in `referral_visits`, one counter per tag per day, with no IP, cookie or user. `sources.ts`'s `referralSources` is the only list of tags and `normalizeRefSource` the only way in: unknown tags are dropped, never stored. Sign-up's optional `ref` sets `users.signup_source` on insert only. The frontend half is `frontend/src/lib/referral.ts` (`captureReferral()` in `main.tsx`)
- **Audit log:** `audit_events` (`schema.ts`), written only through `recordEvent(tx, req, event)` (`src/app/auth/utils/audit.ts`) with the transaction that makes the change, so the row commits or rolls back with it; failures with nothing to roll back (`sign_in_failed`, `admin_reauth_failed`) use `db`. Actions are `auditActions` in `constants.ts`. Actor and target are plain ids (no foreign keys) so rows outlive accounts; a deleted account's email goes in `details`. `pruneAuditEvents` (90 days for `sign_in`/`sign_in_failed`/`admin_reauth`, a year for the rest; the Privacy Policy states both) runs at start-up and daily from `src/index.ts`. `src/scripts/seed-activity.ts` fakes data for development
- `src/scripts/manage-users.ts` (`pnpm admin …` locally, `docker exec ckauth-api-1 node dist/scripts/manage-users.js …` on the VPS, from any folder; `~/Authentication` there is only a git clone, the stack is `/opt/ckauth`): the only way to make, demote or delete an admin, on purpose (see `docs/DEPLOYMENT.md`, "Admins")
- `src/app/middlewares/`: cross-cutting Express middleware (error handler, uploads, `rate-limit.ts`, `request-logger.ts`: pino-http, mounted first, one line per request at a level from `logLevelFor`, `X-Request-Id` on every response; the error handler hands 5xx errors to it as `res.err`). Every endpoint that checks a password, sends an email or takes a single-use token gets a limiter in `routes.ts`, keyed per IP, email or user; keep `docs/API.md`'s rate-limit table in sync
- `src/utils/`: `ApiError`, `ApiResponse`, `logger.ts` (the one pino logger: JSON lines always, `LOG_LEVEL`, default `info`; `pnpm dev` pipes it through pino-pretty), `mail.ts`, `imagekit.ts` (third-party clients live here). `mail.ts` has a `MAIL_TRANSPORT=memory` switch for the tests; production never sets it
- Emails are three files: `emails.ts` (what each says, as data), `email-layout.ts` (one HTML layout for all, with dark mode: `prefers-color-scheme` plus Outlook's `[data-ogsc]`; Gmail ignores both and recolours on its own, so the light palette must survive inversion) and `mail.ts` (sending). Icons are PNGs in `frontend/public/email/`, rendered from `frontend/email-icons/*.svg`, which `frontend/scripts/email-icons.mjs` builds from lucide (Gmail strips SVG). The design is "spotlight" (a tinted top with a big centred icon and title, a pill button); three colour themes (`ember`, `midnight`, `warm`) are candidates until one is picked
- `scripts/perf/` (`measure.js`, `report.js`) + `.github/workflows/perf.yml`: weekly real-world speed measurement of production, results on the orphan `perf-data` branch; read-only against production
- `src/app/dev/routes.ts`: development-only routes (email previews, and `/dev/outbox` for the browser tests), mounted only when `NODE_ENV` isn't `production`; `frontend/src/pages/dev-emails.tsx` (`/dev/emails`) shows them. `check-dist.js` fails a build that ships it, and `check-repo.js` leaves `/dev/` routes out of the Caddyfile comparison
- `src/db/schema.ts` → migrations in `drizzle/`; `src/db/migrate.ts` applies them in production

## Conventions

**Handlers.** Express 5 forwards rejected promises, so handlers `throw` instead of calling `next(err)`. Follow the existing order: validate → query → check → act → respond.

```ts
const {email, password} = await parseOrThrow(somePayloadModel, req.body)
```

`parseOrThrow` (`src/utils/validate.ts`) is the only place that formats a validation error. The frontend's `parseInvalidFields` (`frontend/src/lib/validation.ts`) reads its `Invalid input fields: field: message, …` format to put each error on its field, so change the two together. Build new models from the shared field models in `models.ts` (`emailModel`, `firstNameModel`, `lastNameModel`, `existingPasswordModel`) rather than retyping the rules.

- **Errors:** `throw ApiError.badRequest/unauthorized/forbidden/notFound/conflict/internal(msg)`, or `new ApiError(status, msg)` for other codes (413, 502). Never `res.status().json()` an error directly.
- **Success:** `return ApiResponse.ok(res, message, data)` / `ApiResponse.created(...)`.
- **Signed-in user:** `(req.user as any)?.id`.
- **Logging:** `req.log.error({err: error, userId, …}, 'mail failed')` inside a request (it carries the request ID), `logger` elsewhere; never `console` outside the `src/scripts/` CLIs and `migrate.ts`. A fixed lowercase message with the details as fields, so one search finds every case. Name people by `userId`, never by email.
- **Database writes:** use `.returning({id: usersTable.id})` and check the row, throwing `ApiError.internal` if it's missing.
- **Imports:** relative and ending in `.js` (ESM), e.g. `'../../utils/api-error.js'`.
- **Style:** match the surrounding file. In the controller: single quotes, no semicolons at the end of statements (some import lines have them), and `if(` with no space. Comments are lowercase and explain *why*, not what.

## Security rules (do not regress)

- **Hash every token before storing it:** `crypto.createHash('sha256')` for random tokens (refresh, verification, reset), and bcrypt for passwords. Use native `bcrypt` (thread pool), never `bcryptjs`: on the main thread, each hash stalls every other request. Use `createTempToken()` and `hashToken()` (`src/app/auth/utils/tokens.ts`) for new tokens.
- **No account enumeration.** Sign-up, sign-in and forgot-password return the same response whether or not the account exists. Explain differences by email, never in the response.
- **Unverified users get no session:** sign-in, `/refresh` and `authenticateToken` return 403. Verifying requires the signup password. A password reset also verifies (the link proves the inbox), which is how admin invites finish; it never starts a session.
- **Admins are made only out-of-band.** The API can't create, demote or delete an admin (invites are always `user`; `inviteUserPayloadModel` is `.strict()`); only `manage-users` on the server can. Admin writes need sudo mode (`requireRecentReauth`, password confirmed within 15 minutes). Granting a power must be at least as hard as taking it away.
- **Let the database decide races.** Use unique constraints with `onConflictDoNothing`, conditional `UPDATE … WHERE … RETURNING` for check-then-act (e.g. email cooldowns), and `SELECT … FOR UPDATE` in a transaction when replacing a stored value. Never make a network call (email, ImageKit) inside a transaction.
- **Emails are fire-and-forget:** `sendX(...).catch(error => console.error(...))`. A failed email must never fail the request.
- **Uploads:** authenticate before parsing. Trust the file's magic bytes, not the client's mimetype. Use random filenames (no user IDs in public URLs). Clean up uploaded files on every failure path.
- Never log passwords, tokens or secrets. Log a request by its route template (`routeOf`), never `req.url`: tokens travel in paths (`/verify-email/:token`). The request logger's fields are an allow-list; don't log whole headers, bodies or user rows.
- **Every action that changes an account or is an admin action records an audit event** in the same transaction (`recordEvent(tx, …)`); never write it after the commit.

## Workflow

- **Schema changes:** edit `schema.ts` → `pnpm db:generate` → review the SQL → `pnpm db:migrate`. A change isn't done until the migration is applied, and the migration folder must be committed with it.
- **UI changes:** use the `/ui-change` skill: agree the direction with ASCII sketches first, then build looks in the design lab (`design-lab.tsx`), promote the winner and keep the lab.
- **API changes:** update `docs/API.md` and the frontend in the same change.
- **Deploys:** migrations run automatically before the new API starts, and rollbacks don't undo them, so keep migrations backwards-compatible. New env vars go in `deploy/api.env.sample` and `docs/DEPLOYMENT.md`, and must be added to `/opt/ckauth/api.env` on the VPS before the deploy that needs them. VPS users: `chirag` (admin, sudo) and `deploy` (CI only, no sudo); root SSH is off. `/opt/ckauth` and `/opt/edge` are setgid folders owned by the `deploy` group, which `chirag` belongs to, so scripts must work whichever of the two owns a file (rename into place, don't `chmod` or `chown`). Settings changes need `docker compose up -d api`, not `restart`. `deploy/backup.sh` is the nightly dump. Containers run as non-root with `cap_drop: [ALL]`, `no-new-privileges` and read-only filesystems where possible, so keep it that way when adding services. The production database has no public port and isn't on the `edge` network. Security headers belong in `deploy/ckauth.caddy`, not in the web container. Breaking changes need a `BREAKING CHANGE:` footer in the commit.
- **Commit, PR, docs, search copy, docs artifact:** all in the `/ship` skill (`.claude/skills/ship/SKILL.md`), which runs in a fresh Sonnet subagent. Only commit when the user asks; then use `/ship`. When a rule is added here, add its check to `scripts/check-repo.js` or `frontend/scripts/check-dist.js` and prove it fails once.

## Known gaps

- Rate limits fail open: if Redis is unreachable, requests pass (`passOnStoreError`) and the error is logged. `disableOfflineQueue` makes that immediate; without it every limited request waited ~5 s (`test/redis-down.test.ts`).
- No MFA, for admins or anyone; sudo mode is the interim protection for admin writes. Browser end-to-end tests cover only sign-up and sign-in (`e2e/`), and aren't in CI yet.
- No CORS middleware (not needed while the frontend is same-origin).
- Malformed or oversized JSON bodies return 500, because `errorHandler` only recognises `ApiError` (body-parser errors carry `status` 400/413).
- **SEO and traffic:** the full list, with test IDs and the 33/100 score, is in `docs/SEO-AUDIT.md`. Two rules to keep while building: no opacity modifiers on text (contrast passes WCAG AA), and the `@app` route list in `frontend/Caddyfile` is kept in sync with `src/app.tsx` by hand. Also: the prerendered footer year is the build year until the client re-renders.
